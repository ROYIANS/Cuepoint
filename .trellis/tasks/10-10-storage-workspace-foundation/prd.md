# Workspace and migration foundation

Status: implementation accepted on 2026-10-10; product commit recorded in task.json; archive follows the approved batch. This child depends on the parent task's approved managed-container contract and must finish before checkpoint, plugin or provider implementation begins. Read-only research for the next child may proceed independently.

## Goal

Make imported and generated bytes application-owned at the domain boundary, while preserving the current browser/Dexie behavior. Establish a portable workspace identity and staged-copy contract that a future desktop filesystem adapter can implement without changing business owners.

## Requirements

- Introduce a small workspace module that represents a workspace identity, a stable project-relative location and a device-local root. It must never persist another device's absolute path as an authority.
- Add a managed-copy import primitive for `Blob`/`File` inputs. It must copy into an independent Blob, verify non-empty content and metadata, and return a stable media identity only after the copy is complete.
- Keep existing `putMedia` ownership and history rules intact. Do not change project routing, media slot semantics or generated-provider behavior in this child.
- Make cancellation, zero-byte input, read failure and duplicate display filenames explicit failure cases. A failed copy must not create a ready media row or delete the original source.
- Add migration/fixture coverage for every currently known binary owner that is not represented only by `db.media`, including nested material payload Blobs. The fixture must report unresolved references rather than silently dropping them.
- Keep secrets, cache, device state and active execution claims outside the portable workspace manifest. Do not add a provider, login, native filesystem dependency or real-user migration here.
- Preserve responsiveness for existing large image/video imports: integrity verification must use bounded chunks with opportunities to process cancellation and UI work. Path naming must preserve distinct stable IDs on case-insensitive desktop filesystems.

## Acceptance criteria

- [x] An imported File can be read from the returned managed Blob after the caller's original File is changed or released.
- [x] A failed, canceled or zero-byte copy leaves no ready media row and leaves the source unchanged.
- [x] Two files with the same display filename receive independent stable identities and cannot overwrite one another.
- [x] Workspace-relative references resolve against a supplied device-local root and reject absolute paths, traversal and foreign workspace IDs.
- [x] The fixture enumerates media table records, nested material Blobs, recordings and output references, preserving stable IDs and reporting missing owners.
- [x] Existing media metadata, owner assertions, orphan-history retention and current tests remain green.
- [x] Large-media validation yields between bounded chunks and cancellation stops before persistence; IDs differing only by case do not collapse to the same file path.
- [x] A future desktop adapter can replace the storage implementation behind the module without changing callers that use stable IDs and relative locations.

## Explicitly out of scope

Checkpoint exchange, conflict resolution, provider authentication, managed service APIs, SQLite migration, UI changes, native filesystem packaging and automatic repair/relinking are later child tasks.
