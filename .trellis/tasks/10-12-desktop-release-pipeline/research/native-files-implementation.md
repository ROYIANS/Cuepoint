## Concrete narrower Windows test-package contract — approved

The owner explicitly approved this narrower guarantee on 2026-10-12: “采用这项保证，继续 Windows 测试包（推荐）”. Source implementation now uses an explicit process-recovery policy. It preserves supported file flushing, atomic fresh-target protection and recovery authority, while corresponding-host Windows execution remains pending. It does not establish sudden OS/power-loss namespace persistence.

Accepted contract: first Windows test packages guarantee successful regular-file byte and metadata flushing, NTFS atomic no-overwrite hard-link publication, and intent/SQLite claim recovery after process termination and reopen. They do not promise that newly created directories, hard-link names, stage unlink operations or completion-marker names survive sudden OS crash/power loss. Unix directory-fsync semantics remain unchanged.

Concrete implementation:

1. Split the cross-platform namespace check from regular-file flushing. `namespace_checkpoint` returns `DirectorySynced` on Unix after an actual directory fsync, or `ProcessRecoveryOnly` on Windows after ordinary local-NTFS directory/ancestor validation. It never claims a Windows directory flush. The method and caller comments document that it is not a power-loss barrier. Existing publication callers flush their stage, verify named/open identities, create a no-overwrite NTFS hard link, and use `flush_published_file` to open the final ordinary file with write rights/no-follow flags, check its expected identity and two owned names, and call `File::sync_all` / supported FlushFileBuffers before proceeding.
2. All actual regular writes (SQLite supported VFS, writer markers, staged bytes, JSON completion markers, product binaries, exports) retain `sync_all`; do not swallow actual failure. Use only ordinary writable file handles for file-byte/file-metadata flush. A parent check cannot substitute for this.
3. Root/ancestor/reparse validation and directory leases constrain path authority. Publication still leaves the durable intent before file creation. Keep provenance and link-count distinctions (one owned name versus two interrupted names), flush verified final file, remove stage, revalidate the parent and only then update publication/claim state. SQLite domain/evidence/receipt atomicity is unchanged. Do not replace link with move or introduce an overwrite path in this first protocol.
4. Before-publication identity/file-flush errors are ordinary failures. After destination link success, external Save errors remain `PublishedWithError` (`fileSync`, or existing `directorySync`/`stageCleanup` classification with precise text), with no auto-retry/canceled/rollback relabel. Product-binary interruption leaves intent/provenance and is reconciled on reopen; never invent ready domain rows or delete unproven bytes. Actual SQLite uncertain outcomes remain existing durable-outcome semantics.
5. File-flush failure after hard-link creation retains the final name and stage provenance; do not clean a name whose authority is unproven. Recovery must verify both names/identity/link count and retain ambiguous external bytes. Unknown or failed recovery is visible and blocks mutation/replay.

Required corresponding-host gates: actual Windows x64 NTFS file identity and hard-link tests; root/database/writer/ancestor replacement and junction cases; regular-file flush with raw flags/results; deterministic interruption at intent/stage/link/unlink/claim boundaries; separate subprocess termination/reopen exact-byte/row tests; existing-target protection; real postpublication flush failure warning; full normal SQLite UI import/remove-source/reopen. Passing process tests never claims power-loss proof. Actual current Windows execution has not happened.

## Primary evidence

- [Directory Handles](https://learn.microsoft.com/en-us/windows/win32/fileio/obtaining-a-handle-to-a-directory): documented directory operations do not list FlushFileBuffers.
- [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers): needs writable handle; volume-wide flushing needs administrative privileges. No elevation is planned.
- [File Caching](https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching): file metadata flushing/write-through is documented; this is not the same as a Unix parent-directory fsync.
- [GetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle): actual volume/index/link state, not superficial metadata.
- [GetVolumeInformationByHandleW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumeinformationbyhandlew): filesystem name/capabilities from the actual handle; unsupported queries remain errors.

## Approved-policy source result

`paths::NamespaceCheckpoint` distinguishes the actual platform strength in names, return values, comments and tests. All old `paths::sync_dir` references were replaced, including retained prototype import/recovery, fresh-root/directory creation, copied targets, completion JSON, full-product setup, external Save and retained desktop acceptance report. Unit-returning wrappers preserve callers' types. Unix directory proof checks device/inode/type, not nlink: creating a child legitimately changes directory nlink. A deterministic child-create test proves real directory fsync still succeeds and object replacement still fails.

`flush_published_file` binds the final no-follow named snapshot and actual descriptor to the expected volume/index, exact owned-link count, byte length and modification state before and after an actual file flush. Windows `open_flush_file` requests write access, sets `FILE_FLAG_OPEN_REPARSE_POINT` and uses explicit read/write/delete sharing. Held ordinary directory handles forbid active ancestor rename. The helper is used by completion JSON, retained import, full-product binary seal/recovery, normal Save and the closed SQLite backup snapshot. No actual flush failure is swallowed. The audit found no remaining Windows-capable `File::open(...).sync_all()` reader-only flush; Unix directory/ordinary-file branches retain their supported descriptor behavior.

Binary seal failure after publication leaves both proven names and the intent. Recovery flushes the verified final file before removing a proven stage or advancing publication state; it preserves complete bytes as unclaimed material and never invents a domain row. Normal Save reports `PublishedWithError { code: "fileSync" }`, retains published bytes, closes the transfer and forbids canceled/retry relabeling. Existing stage cleanup conservatively refuses replaced or aliased bytes. Before SQLite initialization, Windows startup leases pin ancestors; Boundary and managed binary/export leases continue holding them for their active lifetimes.

New reachable tests flush actual owned descriptors before injecting a later failure; they assert post-link `fileSync` semantics, retained intent and idempotent no-invented-claim recovery. Path tests reject wrong/replaced identities and same-ID/same-size mutations. The closed-snapshot regression creates an actual SQLite file, runs the production backup flush, compares unchanged bytes and exact identity/link count, and reopens the row. On Windows that same test reaches the writable descriptor; a reader-only FlushFileBuffers implementation would fail.
