# Research: Remaining business detail links and retained batch-review handoff

- Query: Which remaining Agent entity links can reuse existing editable details, and how can a modal batch review yield to that detail and return without losing its review session?
- Scope: Internal source investigation only; preparatory E16 design while E04 is active. No task activation, product/spec/metadata edits, commands that change Git, tests, builds, network, or provider requests.
- Date: 2026-10-15

## Findings

### Existing contract and bounded recommendation

E01 already delivered the shared no-drawer `ContextPanel` surface and editable single-shot detail. Its results are recorded in `.trellis/tasks/archive/2026-10/10-15-agent-parallel-details/research/implementation-results.md` (commit `5f8b6ab0`). The remaining defect is link coverage and modal handoff, rather than another shared drawer replacement. The current parent roadmap keeps E16 after the early UX work; this investigation does not reorder or activate it.

Recommend a first coherent E16 slice covering **existing shots plus all four exact asset kinds, in project and studio ownership, including both batch-review target entry points**. Those are all `ProductionTarget` variants (`features/video/models/production.ts:5`) and reuse mature editors. Record the coverage boundary explicitly; this first slice does not finish every entity family. Material, IP and memory have identifiable owners but need a separately bounded follow-up slice. Project/episode workspace links and audio/music project links must retain their present meaning until their own detail contracts are implemented. The task PRD explicitly allows converging a bounded rollout rather than recreating every editor at once.

Relevant contracts: `.trellis/spec/frontend/agent-business-details.md`, `feature-organization.md`, `desktop-ui.md`, `agent-activity-ui.md`, and `interaction-feedback.md`; `.trellis/workflow.md`; E16 `prd.md`; parent `roadmap.md` and `research/parallel-detail-navigation.md`. Preserve E01's owned reads, field CAS, synchronous dirty reporting, pending-save protection, stable portal across widths, and real-route departure guards. Preserve quiet normal results: opening/closing details needs no success toast or transient preparation status.

### Reuse the actual asset editors, with their missing panel guards supplied

All four asset pages have feature-owned detail bodies, media slots and field commands. For example, `CharacterDetailPage.tsx:12-41` keys the route owner and query envelope by owner+entity; `:60-83` uses `EditableGenerationSlot`, frozen target keys and `patchCharacter`/`setCharacterSlot` baselines. Scene/prop/style use the same pattern. Extract these bodies behind named feature exports so routes and parallel details share actual fields and commands. Do not copy four new forms into the app layer. Existing read ownership still needs the row's `projectId` checked against the explicit project/studio owner.

Wrapping the current whole page in a panel is insufficient. `features/library/ui/AssetTextField.tsx:8-29` has debounced drafts but does not expose an unavailable flag or departure-state reporting; text changes do not aggregate into the panel guard. Current last-record retention at `CharacterDetailPage.tsx:32-35` only tracks open media editors. Read failures also need panel-local handling rather than an outer boundary replacing the Agent.

Use the existing E01 `app/drafts/TextDraftField.tsx:24-51` contract (or adapt the asset wrapper to it) for synchronous dirty reporting before the React state update, field pending/error aggregation, unavailable controls and disabled retry. Reuse `useManualDraftDeparture` and the shot's feature-owned active/requested target pattern. Keep the matching dirty record snapshot when deleted/unavailable, disable all writes, and show a local read/retry error. A save must retain its original owner/entity/field/baseline even while another target is requested. Include slot editor dirty/pending state; their existing local guards must not be bypassed.

`MaterialDetailPanel.tsx:48-79` already has active/requested identity and its own `ContextPanel`, and `:90-116` has manual revisioned draft/pending state. Reuse that panel directly if material is selected in a later slice, not a nested ContextPanel wrapper. Its query currently lets read exceptions escape and needs local read-error handling for Agent use. `ProjectSettingsPanel` reports output state only for that subset; it is not proof all project text/style changes already participate in a whole-panel guard. `MemoryEditor`/IP editor need body/session extraction from their current dialogs before they can become in-pane editors.

### Cross-family replacement must preserve the outgoing owner

`app/layout/ContextPanelHost.tsx:40-75` already arbitrates registered panels: it invokes outgoing `depart`, closes it only after acceptance, cancels the incoming panel when departure is refused, and invalidates stale competing requests. Same-family A→B changes remain the feature panel's active/requested responsibility (`ShotDetailPanel.tsx:30-80`). Keep those boundaries.

Avoid a provider implementation that immediately switches a single discriminated render from `<ShotDetailPanel>` to `<AssetDetailPanel>`: it unmounts the outgoing shot owner before the host can ask its guard. The smallest compatible composition is a finite app facade with independently retained feature-family panel owners (shot and asset initially), each registered with the existing host until its guarded `onClose` occurs. The app may request the incoming family while the outgoing family remains mounted for arbitration. An alternative coordinator must provide the same retained outgoing-owner guarantee, not just switch a union target. This is explicit composition, not a plugin registry or generic editor framework. Add only exact named cross-feature exports to `quality/studio-ownership.json` if implementation needs them.

All new panels keep E01's single portal, measured width and full-width fallback. `ContextPanelHost.tsx:77` uses navigation width + requested panel width + 480px center; no extra viewport breakpoint or narrow-screen drawer. `app/layout/context-panel.tsx:37-65,103-129` retains host registration, focus scope and return control. Do not navigate, arm route-bypass tokens, abort the conversation or remount its owner to inspect details.

### Retained batch-review handoff: smallest state/ownership change

`features/agent/ui/AgentGenerationBatches.tsx:129-188` is already a suitable retained owner: `BatchSurface` holds local `{revision, edits}`, expanded item, target group, pending+pendingRef, errors, outcomes and the scoped batch query outside the Dialog content. Its router/unload blocker is also outside the content. `persist` uses the frozen local revision/edits (`:199-210`); `action` has a synchronous lock (`:213-227`); approval explicitly persists and confirms the exact batch revision (`:234-239`). Preserve these owners and command calls unchanged.

Current normal close refuses dirty/pending review (`:249-255`). Handoff must be a separate presentation transition rather than calling `onOpenChange(false)` or discarding/saving the local draft. Proposed local state is a bounded `handoff` record: token, originating batch ID/session, typed detail target, item/control bookmark, body scroll position, and return intent. Keep `open`/review-session ownership separate from whether modal content is currently presented. No durable schema or global workflow store is required.

1. On an ordinary target activation, capture the review scroll/focus bookmark and request a handoff. Keep the existing batch controller, local edits, chosen target, expanded state, pending promise and approval identity mounted. Modified/middle clicks retain real-anchor navigation behavior.
2. Temporarily close/unmount the review Dialog content/overlay while retaining `BatchSurface`. Wait for that modal presentation to release its focus/inert boundary before requesting the feature detail. The current portal is inside `.agent-chat-root` (`:182`) and its content is modal (`:274-282`); placing the detail beside it is not enough. Do not rely on `forceMount` plus visually hidden modal content to release modal accessibility/scroll side effects.
3. Suppress the current unconditional close autofocus to `triggerRef` (`:279-282`) during handoff; focus the actual opened detail. Only one modal/detail transition may own a return token. If host arbitration refuses the incoming detail, its close/cancellation returns to the same review instead of leaving it hidden. Late completions must match the original token/session before restoring anything.
4. Add the explicit detail return action “返回批量审阅” for this origin in both widths; the shared return bar is hidden when docked, so a return-label prop alone does not create a visible wide-screen action. Return first passes the detail's normal dirty/pending guard, then closes it, restores the exact originating review presentation and restores its group, expanded row, scroll and stable control bookmark. A DOM input may remount when modal presentation closes; preserve its controlled value/caret bookmark rather than claiming the same input DOM is retained. Generic Agent details keep “返回对话”.
5. A pending review save may settle in the retained controller while details are inspected; no abort, duplicate save, automatic confirmation, generation or writeback is introduced. Preserve its receipt/error on return. Opening a detail must not call `persist`, `confirmGenerationBatch`, `startGenerationBatch`, selection/apply commands or any provider.
6. If editing the target makes its old batch baseline stale, the existing revision/approval/apply checks still decide the later action. Do not refresh an approved target snapshot automatically or treat inspection as renewed consent. An explicit reveal/open of the originating batch while handed off must resolve the same return path, not create a second review session.

Keep the existing candidate-media preview modal's purpose separate (`AgentGenerationBatches.tsx:499-549`). This task concerns the two business-target links, not redesigning generation comparison or approval into another surface.

### Implementation ownership and necessary verification

Suggested bounded ownership: app bridge/parser and exact allowlist integration; library asset editor extraction/panel/query/field guards; Agent batch-local handoff/focus restoration. Coordinate the bridge props before parallel edits; `AgentChatPage` needs only the provider composition change, not modifications to runtime, send flow, query hooks or scroll owner. No package, schema, provider, build or bundle-configuration changes are needed for this design.

Existing useful tests, all in the repository-root `tests/` directory: `shotDetailTarget.test.ts`, `shotDetailPanel.test.ts`, `shotDetailQueryLifecycle.test.ts`, `e01ManualDraftDeparture.test.ts`, `contextPanelCoordinator.test.ts`, and `contextPanelDom.test.ts`. `createdEntityLinksCollapse.test.ts` exercises rendering/collapse but its Link mock currently omits click behavior, so it does not establish activation coverage. Existing `agentGenerationBatch*.test.ts` exercise durable batch/revision/safety commands; they do not establish actual modal handoff/focus behavior. Use the existing real ProductStore/controlled transport test patterns rather than source-string assertions.

Minimum meaningful changed-scope cases:

- Finite canonical/hash asset parsers for four kinds and both ownership modes; reject foreign/absolute/malformed/ambiguous hrefs consistently with E01. Unsupported collection/workflow links retain navigation; modifiers retain anchor behavior.
- Actual asset editor queries for matching project/studio ownership, empty/foreign/late/error reads; synchronous input→immediate replacement/close; pending saves frozen to original target; deleted dirty records retained with all writes disabled. Parameterize the four existing kinds without duplicating every field test.
- Cross-family shot→asset replacement: outgoing dirty editor survives refusal; acceptance happens once; competing/late requests do not unmount the wrong owner. Keep E01's stable editor DOM/caret/scroll across docked/full-width transitions.
- Actual batch UI: edit prompt/inclusion, expand and select a target, open its detail; verify modal releases keyboard/inert boundary and no confirm/start/provider request occurs. Return restores the same draft/revision/group/expanded/scroll/focus state. Repeat with pending save settlement and a refused outgoing-detail guard.
- One retained Agent owner check across detail opening and batch return, covering an active execution and paused message-follow state; preserve E02 canonical join and E04 reading behavior without rerunning unrelated full suites.

The existing repository-root browser fixture `tests/fixtures/agent-parallel-details/harness.tsx` is a useful later integration seam. Full browser/native/build/package acceptance remains at the user-selected batch end. No checks were run during this research.

## Caveats / Not Found

- No critical new user preference is required for the first coherent slice: editable details, no drawer, retained running conversation, narrow full-width fallback and per-stage bounded validation are already explicit owner decisions. Selecting subsequent entity slices is a scope decomposition decision; do not block the authorized core work on re-approval.
- Do not mark “all business links complete” after the first slice. The coverage table deliberately retains project/episode/IP/material/memory/audio/music follow-ups with concrete owners and missing identity/body contracts. The parent should keep these residuals visible when converging E16 scope.
- Several old links lack entity identity. Existing result summaries sometimes contain IDs elsewhere, but no guaranteed typed association from each rendered href was found; selecting the first result or parsing its label would be unsafe.
- This is a source-backed design, not measured native/browser acceptance. E04 is moving in shared Agent UI; line numbers can shift. No source, spec or task lifecycle metadata was changed. No external references were needed.
