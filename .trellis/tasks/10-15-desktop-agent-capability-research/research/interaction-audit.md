# Research: Desktop Agent interaction audit

- Query: How should Cuepoint respond immediately to Send, and which adjacent interaction gaps are supported by its actual code when compared with DeepSeek Harness?
- Scope: mixed — Cuepoint product/source/specs and a local external reference; interaction only, without repeating the capability/architecture audit.
- Date: 2026-10-15
- Baselines supplied by the parent task: Cuepoint `9d1a41739b17be27cf832326de15a9489017825a`; DeepSeek Harness `571902028a75c64c1d767f4ae5fd099485f0ddf0`, `0.2.1-alpha.3`. No Git operations were run by this researcher.
- Path convention: unprefixed paths below are relative to `/Users/xiaomengdao/WebstormProjects/aifenjing`; `DSH/` expands to `/Users/xiaomengdao/WebstormProjects/deepseek-harness/`.
- Method: static source tracing. No app launches, installs, model requests, runtime timing measurements or product changes. "Can wait" identifies an awaited dependency, not measured user-visible lag. Synchronous state registration is not proof of a completed browser paint; even DSH's `nextPaint` provides an opportunity with a timeout fallback. A strict claim that pixels precede the start of a network request would require a browser performance trace. Priorities below are proposed delivery order, not production incident severity.

### 2. Prioritized user-facing gaps

#### I1 — P1: Send does not immediately move the submitted content into the conversation

**Source fact.** The synchronous `sending` state changes the button, but there is no submitted text/attachment echo or draft clear until the awaited steps above complete. On a new topic the user also waits for persisted creation and navigation before reaching the transcript. An accepted first message can additionally encounter the rich-transcript loading fallback. The current interface therefore cannot satisfy the owner's explicit "click Send changes the interface before requests" requirement if that means seeing the submitted content in its destination and an empty input ready for the next draft.

**Small proposal.** Capture an immutable, session-scoped submission before the first awaited operation: stable local attempt ID, exact text, selected attachment revisions, intended thread/home scope and draft revision. Paint a provisional user row, move the submitted payload out of the composer, and retain later edits independently. Keep a concise pending indication distinguishable from confirmed local acceptance. Reconcile that row with the actual durable user/run identity; do not add a second bubble when observation arrives. For first send, the provisional conversation surface must exist before waiting on native thread creation; preserve the existing bind-before-navigation ownership rule.

**Why the reference helps.** `beginSubmission` + shared request identity + observed retirement is a concrete pattern for registering a displayable echo before awaited work, without duplicate durable rows. DSH deliberately renders its transcript echo exactly like a durable user row (`DSH/packages/client/ui-chat/src/client/chat/MessageItem.tsx:174`, `:251`); Cuepoint should still make pending/failed acceptance understandable. Copying that visual sameness is not necessary.

**Preserve.** The actual model request must still wait for compatibility, thread ownership and atomic `beginAgentRun`. A provisional row authorizes no tool, paid request or saved-result claim. Existing `useReferenceDraft` revision comparison prevents a later acknowledgement from erasing edits made during admission (`packages/studio/src/features/agent/ui/useReferenceDraft.ts:144`).

#### I2 — P1: Preparation, provider waiting and live text share too little feedback; text publication depends on storage

**Source fact.** One page-local `sending` boolean spans model verification, thread creation, context work, transport, tool execution and final persistence. Before the run record exists, the main guaranteed feedback is the Stop icon; `正在执行` depends on observing a running run. After acceptance the same general progress label covers different waiting boundaries. For providers requiring validation, Send repeats discovery even if a catalog already exists; this is an actual awaited GET, not a measured cost (`connectors.ts:90`).

**Source fact.** Every visible delta currently travels through the writer, Studio's transactional checkpoint, native commit/change notification and a fresh query snapshot. The writer coalesces pending snapshots and preserves monotonic checkpoints (`packages/agent-core/src/checkpoint.ts:10`, `:28`); it is not a fixed time debounce. Native writes await commit and changed-row reads before returning (`packages/studio/src/platform/storage/native.ts:495`, `:525`, `:406`); observations then take an admitted readonly transaction (`:345`). That path may wait behind other native roots (`:446`). First visible text can consequently trail receipt of the first provider token. Its duration is unmeasured.

**Small proposal.** Present a few honest stages derived from real boundaries: preparing submission, waiting for model, receiving output, waiting for user action, stopping/saving. Preserve the quiet transcript design; no per-token announcements or fabricated percent complete. Record click, echo paint, durable begin, model dispatch, first received delta, first displayed delta and final persistence separately before choosing a performance optimization. The existing core unconfirmed-output observer is a candidate for a run/execution-scoped live text overlay, with committed snapshots as the recovery floor. Stop/ownership changes invalidate that overlay; a save failure must remain visible and cannot be called completed. Do not delete durability/flush safeguards to improve animation.

#### I3 — P1: A pre-accept failure has weak recovery context, and retained drafts are only page memory

**Source fact.** Before `beginAgentRun` succeeds there is no message/run to carry a failed-send state. The parent catches failures with `showError("发送失败")` and leaves the draft (`packages/studio/src/features/agent/ui/AgentChatPage.tsx:430`). The user can resubmit, but the transcript cannot show which attempt failed or offer a contextual retry for it. `useReferenceDraft` stores its per-scope drafts in `useState`/refs only (`useReferenceDraft.ts:23`, `:39`); leaving the Agent page or reloading discards that unsent recovery payload. This is a source-backed persistence limit, not evidence of a reported data-loss incident.

**Small proposal.** Make I1's submission an explicit recoverable UI object: distinguish preparation/admission failure from an already-accepted model failure, retain its payload, and offer retry/edit/dismiss in context. Restore into an unchanged/empty composer, or preserve it as a separate failed draft if the user has typed something new. Decide explicitly whether unsent textual drafts survive reload; do not persist keys, raw local File objects or invented business results. A local acceptance outcome may be unknown: native commit/status reconciliation can throw `UnknownCommitError` (`packages/studio/src/platform/storage/native.ts:510`). Query by stable intent/durable identity before resubmission rather than treating every caught exception as "nothing happened".

**Already good.** Once accepted, explicit text-only retry creates a new assistant/run using the original user message and frozen request context (`packages/studio/src/features/agent/commands/agentRuns.ts:50`, `:90`, `:112`, `:141`). Tool runs use saved continuation; failed/partial output is kept and error text stays separate. Same-tick duplicates are blocked by a synchronous ref, cross-page competition by the per-thread Web Lock (`useChatExecutionSession.ts:23`; `runtime/runOwnership.ts:46`). No evidence here that ordinary double-clicks currently duplicate requests.

**Reference limit.** DSH restores detached failures without overwriting a nonempty newer draft (`DSH/packages/client/ui-conversation/src/client/input/facade.ts:764`) and persists semantic drafts per session (`DSH/packages/client/ui-conversation/src/client/stores.ts:22`, `:43`). Its failed detached payload is not a persistent outbox, and its prompt failure surface is a transient toast (`DSH/packages/client/ui-conversation/src/client/skeleton/InputBar.tsx:101`). These are useful patterns with limits, not a complete recovery UX to copy blindly. Host request-ID checking (`DSH/packages/api/session-controller/src/commands.ts:321`, `:584`) is admission dedupe, not a universal tool-effect exactly-once guarantee.

#### I4 — P2: Stop does not acknowledge the stopping phase immediately

**Source fact.** `handleStop` aborts the controller and pauses audio batches, without setting an acknowledged/stopping UI state (`packages/studio/src/features/agent/ui/AgentChatPage.tsx:375`). The Stop button and general sending lock remain until the entire flow settles (`useChatExecutionSession.ts:32`). This is safe for admission/flush ownership but gives no new indication that a press was received. Model/tool terminal state also awaits checkpoint flush and saved settlement (`packages/agent-core/src/runtime.ts:211`, `:238`).

**Boundary to test.** The flow checks abort before `updateChatThread`, but not again between that awaited update and `beginAgentRun`; the latter has no AbortSignal input (`chatExecutionFlows.ts:110`, `:123`; `agentRuns.ts:58`). Stop during this local admission window may still yield an accepted user/run followed by cancellation. The UI should clearly express whether it is canceling an unaccepted submission or stopping accepted work; it must not imply that completed effects were undone.

**Small proposal.** Immediately change to an idempotent "正在停止…"/"正在保存已收到内容…" state, keeping the existing lock until authoritative settlement. Preserve partial text, completed receipts and unknown tool outcomes. Define the pre-accept cancellation policy and recheck signal at safe dispatch/admission boundaries; aborting a commit already in flight is not proof of rollback. DSH's ordinary `Session.cancel()` also waits for authoritative remote state without an immediate cancel snapshot (`DSH/packages/api/session-controller/src/client/sessions/session.ts:347`), so it is not a superior general example. Its Jobs UI is a better local model: `pending` remains until the authoritative status frame arrives (`DSH/packages/client/ui-jobs/src/client/JobListAction.tsx:430`).

#### I5 — P2: Topic switching has an empty/loading ambiguity and an unscoped departure predicate

**Verified protection.** There is no supported claim of old messages appearing under a new topic: `AgentChatPage.tsx:716` keys ChatWorkspace by `activeThreadId` and explicitly filters its messages/runs by that ID at `:725`; `currentRun` is also filtered at `:564`. The shared Agent parent remains mounted across topic routes (`packages/studio/src/app/routes/_studio.agent.tsx:9`).

**Actual source window.** `useProductQueryState` retains the previous successful result while new dependencies load (`packages/studio/src/platform/product/queries.ts:5`, `:17`, `:26`). Messages/runs return bare arrays, without a requested-thread envelope (`AgentChatPage.tsx:162`, `:171`). An old nonempty array is filtered to `[]` for the new topic and passed as a loaded empty thread; ChatWorkspace only renders loading for `messages === undefined` (`ChatWorkspace.tsx:119`, `:127`). Task empty-state copy can also appear prematurely. Separately, `useThreadDeparture(activeThreadId, runs)` receives the unfiltered retained run array (`AgentChatPage.tsx:180`); its active/executing predicates do not check `run.threadId` (`packages/studio/src/features/agent/ui/useThreadDeparture.tsx:29`, `:38`). During the new query's wait, an old blocking run can therefore participate in the new topic's leave decision. Actual screen timing/reproduction remains to be tested.

**Small proposal.** Return `{forThreadId, messages/runs}` even for empty results and gate the view/actions until that identity matches. Filter the departure predicate to its owned thread, while preserving confirmation for truly active work. Avoid remounting the parent execution/draft owner just to hide a retained-query result. This follows the existing `hook-guidelines.md` changed-dependency contract and the already-correct scoped envelope in `AgentComposerAttention.tsx:28`, `:33`.

#### I6 — P2: Reading older content lacks a direct "back to latest" affordance

**Source fact.** Cuepoint correctly stops following when the user scrolls away or reveals process details, and resumes on a new user turn (`packages/studio/src/features/agent/ui/MessageList.tsx:56`, `:74`, `:109`). Follow intent is held only in refs; the rendered list has no back-to-bottom control (`:96`). The turn rail appears only from five turns (`TurnNavigation.tsx:71`) and targets user anchors, not the latest streamed line. The workspace remount/initial layout also snaps to bottom on each topic visit (`MessageList.tsx:64`; `AgentChatPage.tsx:717`), so an older reading position is not retained.

**Small proposal.** Add an accessible "回到最新" control whenever following is paused, optionally with a quiet indication of newer content. Clicking it resumes following; streaming must never seize the reader's position. Consider per-topic reading restoration separately if desired; do not make it a requirement of optimistic Send. DSH already renders this affordance when `!followingTail` (`DSH/packages/client/ui-chat/src/client/chat/ChatView.tsx:240`) and treats new local submissions as own-input scroll events (`use-chat-scroll.ts:67`). Keep Cuepoint's instant stream scrolling; its spec explicitly rejects copying another product's send animation/virtualizer without a measured need.

### 3. Approval, progress and navigation behavior to preserve

- **Approval is already visible and recoverable.** Pending processes open on a status transition; manual folding survives later updates. Generic approve/reject buttons sit outside the individual call's collapsible payload (`packages/studio/src/features/agent/ui/AgentRunDetails.tsx:101`, `:135`, `:239`). Generation/music retain their own review/confirmation UI. Do not add a duplicate approve action to the optimistic bubble or composer reminder.
- **Reminders already outlive a model answer.** `AgentComposerAttention` independently queries calls/batches/items/jobs/tasks, tags its own thread identity, displays read failure and reveals the relevant process instead of authorizing it (`packages/studio/src/features/agent/ui/AgentComposerAttention.tsx:19`, `:33`, `:48`). Completed model output is not a reason to hide pending batch review. DSH's approval panel also claims a synchronous ref and immediately marks busy; it restores answerability on rejection (`DSH/packages/client/ui-approval/src/client/ApprovalPanel.tsx:36`). Cuepoint already synchronously acquires execution for run actions (`AgentChatPage.tsx:478`); the useful extension is action-specific pending copy, not a second approval system.
- **Rejection is persisted independently of model availability.** Cuepoint saves approve/reject before resolving the connector for continuation (`chatExecutionFlows.ts:190`). Offline/missing credentials must not erase a refusal or falsely state that an approved tool executed.
- **Navigation deliberately stops the current local run.** Topic selection and route Back go through confirmation, and route identity changes abort the old controller (`AgentChatPage.tsx:182`; `useThreadDeparture.tsx:44`; `useChatExecutionSession.ts:19`). Saved partial text/steps remain resumable. That is the current product contract, not an accidental defect. Supporting background execution needs a separate owner/lifetime decision; the existence of job records is insufficient.
- **Progress and completion truth are already separated.** `AgentRunDetails` shows tool/process state and `AgentWriteOutcomes`; failed/unknown effects remain explicit, while receipt-based saved results carry business evidence (`AgentRunDetails.tsx:130`, `:276`). Preserve the existing quiet success design and do not make optimistic sending imply durable acceptance, model completion, tool success, provider-job completion or acoustic/creative acceptance.
- **Optional product direction, not a finding:** Cuepoint lets users type during a run, but send/attachment mutation are disabled until execution settles (`FloatingComposer.tsx:190`, `:358`; `AgentChatPage.tsx:585`). DSH permits queue/steer submissions and has an editable queue dock, with provisional queued items nonactionable until admission (`DSH/packages/client/ui-conversation/src/client/input/machine.ts:128`; `DSH/packages/client/ui-conversation/src/client/queue/QueueDock.tsx:100`). Adopt only if users need mid-run steering or queued turns; enabling Send without implementing admission, queue ownership, cancellation and approval implications would be unsafe scope expansion.

### 5. Recommended first delivery slices

1. **Submission presentation plus recovery (I1 + the pre-accept part of I3):** immediate echo/clear, immutable attempt/scope identity, observed handoff, failure edit/retry and newer-draft preservation. Stable IDs and uncertain-acceptance recovery belong in this slice, not a later cosmetic patch. Keep the durable command and provider/tool contracts intact.
2. **Honest pending/stopping states plus timing evidence (I2 + I4):** visible preparation/model-wait/stop acknowledgement and event timestamps. Add a live text overlay only after measuring its benefit and proving save-failure/ownership behavior; the core already provides unconfirmed events as a possible seam.
3. **Query identity at topic boundaries (I5):** loading envelopes and owned departure predicates, with a slow-read scenario. Small scope and a correctness improvement independent of any broader desktop capability expansion. The scroll affordance (I6) can follow as a separate small UI improvement.

## Caveats / Not Found

- This report does not establish click-to-paint, bridge, first-token or scroll latency in milliseconds; no runtime regression has been measured. Delay/fault acceptance scenarios are proposals.
- The initial suspicion of cross-topic transcript leakage was disproved by `AgentChatPage.tsx:725` filtering and the keyed workspace. The narrower loading/departure findings are the supported conclusions; do not repeat the leakage claim.
- No blanket assertion that Cuepoint has no optimistic behavior: `setSending(true)` and other revision-safe UI updates are already immediate. The missing behavior is the submission-content echo/clear before awaited work.
- No duplicate-request defect was established for normal rapid submit. Stable provisional identity is a requirement for the proposed new presentation path and uncertain acceptance recovery, not evidence that existing locks fail.
- DSH is not uniformly more immediate: reference-chip/slash preparation can precede its ordinary echo, stream publication is intentionally frame-batched, transcript echoes are visually identical to accepted rows, and ordinary stop lacks a distinct pending snapshot. Its transient error/restoration paths do not constitute a durable outbox.
- Background execution, queues/steering, virtualization, guaranteed draft durability and per-topic reading restoration are product choices. Existing stop-on-departure, explicit approval and receipt-only success are preserved contracts, not defects to remove.
- Research owns only this file; no product code, specs, task state, model/provider execution, reference worktree or Git state was changed.
