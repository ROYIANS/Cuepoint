# E03 execution feedback design

## Scope and authorization

The owner authorized sequential delivery and a commit after each completed stage. Activate this child only after E02 is checked and committed. Use E02's final submission/recovery contracts rather than introducing another attempt owner. Exact phase copy and transient, content-free timing are routine design choices within the requested outcome. No new product decision blocks this scope.

## Phase and execution ownership

One small invocation-owned feedback controller projects `preparing`, `waiting_model`, `receiving`, `working`, `waiting_approval` and `stopping` from actual boundaries. Bind it to the existing execution token/thread/run and reject older callbacks. The Stop handler publishes stopping synchronously before abort; repeat Stop is disabled/idempotent. Retain the existing send lock and Web Lock through authoritative flush/settlement and final release. A completed transaction wins over late cancellation; no text/effect rollback is implied.

Preparing starts with the valid local attempt and actual context preparation. Waiting starts at the application fetch supplied to the main protocol adapter, after reference materialization. Receiving requires nonempty public content/reasoning; tool argument fragments do not count. Tools use working and existing process rows. Approval continues to use the existing durable call/attention owner. Keep preparing/receiving internal and quiet; use the existing waiting surface only during actual main-request waiting and `正在停止…` for explicit Stop. The owner also rejected the automatic `正在确认 APIMart 模型类型…` warning; unresolved background probing produces no warning while actual validation/send guards and resolved incompatibility errors remain. Reuse the existing composer execution strip and button accessible labels; do not add another progress line or expose every internal storage/loading step. Keep completed transcripts quiet and retain E02's distinct failed/unknown admission UI.

Use Studio's optional host wiring and the core's existing invocation-scoped output/checkpoint/approval/settled observer. Keep the reusable loop, writer, providers and native transport policy unchanged. Actual selected fetch arguments/signal/current credential resolution must pass through unchanged. Do not treat an auxiliary compaction request as main-model dispatch.

An owned plain reply stays quiet during its final flush/metrics/settlement. Internal working after transport return does not add a generic execution strip; an old running query cannot bring the strip back after this invocation releases. Keep actual operation/approval feedback with its existing owner. Independent review exercises these held windows through the actual page.

## Timing and visibility

Use one monotonic clock and content-free invocation identity. Record submitted, actual provisional DOM commit, known admission, application request invocation, first nonempty public receipt, first confirmed output checkpoint, actual first public DOM commit, explicit stop, confirmed terminal settlement and final release separately. Omit marks with no observed boundary; a lost acknowledgement followed by positive reconciliation records the time admission became known rather than a fictional original COMMIT timestamp. Do not reinterpret existing provider throughput metrics.

Standard prefixed User Timing marks provide developer retrieval without a new global API, settings screen, console content log or uploaded telemetry. Keep at most eight invocations and 256 owned entries, clear exact names only, feature-detect and isolate diagnostic failures from execution. Dispose the controller's entries when its owner unmounts. Never store text, references, credentials, URLs, errors or creative content in trace names/detail.

First display must correspond to this invocation's confirmed output lineage at the actual visible answer/current-process or open reasoning body. Old saved content on resume, folded reasoning and an inert chat behind narrow shot detail cannot count. Explicitly call these DOM-commit/visibility-eligibility measurements; they do not prove compositor pixel paint or live latency improvement.

## Boundaries and acceptance

No live-text overlay is selected: the source investigation collected no timing evidence that warrants changing publication/checkpoints. No schema, dependency, shared-core protocol, background host, remote cancellation promise or durable analytics. Necessary tests cover phase ownership, immediate repeat-safe Stop, held begin/flush settlement, content-free bounded timing, actual DOM correlation and both existing protocol callbacks. Full suites, builds, packaging and native acceptance remain deferred to batch completion.
