# Research: Desktop background execution and a single product instance

- Query: Which desktop host can support multiple running conversations after closing the one product window, and how can reopen, repeated launch and explicit Quit preserve one execution/store owner?
- Scope: mixed — current source, locally installed pinned dependency source, official platform/API documentation and the published plugin crate.
- Date: 2026-10-16

## Findings

### Recommendation

Use one application-level TypeScript execution service in the **retained existing main WebView**, backed by the existing Rust services and sole ProductStore. Close means prevent destruction and hide; reopen shows/unminimizes/focuses that same window. This is the smallest defensible first implementation for the confirmed lifetime: application-managed work while the application remains alive; explicit Quit ends it. It does not promise survival of renderer crash, OS sleep, force quit or application exit.

On macOS set the supported background scheduling policy to disabled; on Windows retain normal WebView2 execution without calling TrySuspend. Do not use production Chromium flags or visibility/DOM/rAF callbacks as execution progress owners. Treat a real long-hidden run as a necessary platform gate rather than infer success from retained objects. A Node sidecar is not justified merely because Tauri's background policy setter is unsupported on Windows.

Strict single-instance admission must happen **before creating main**, not when the first product query opens SQLite. Choose a lifetime-held native file lock plus a small native activation-only loopback endpoint using existing Tokio. Activation can only show/unminimize/focus the existing main window; it never changes routes, submits a run, supplies a filesystem path or forwards arbitrary launch arguments. **No single-instance plugin or new crate is required.** The official plugin was compared below and rejected for this task because its macOS fail-open/asynchronous endpoint paths still need a separate strict fence.

### Background scheduling: exact supported APIs and limits

- **macOS is 14.0+, not 14.3+.** Installed `tauri-utils-2.10.1/src/config.rs:2235` documents `backgroundThrottling`; `wry-0.57.0/src/wkwebview/mod.rs:473` maps Disabled to `WKInactiveSchedulingPolicy::None`, applies it on macOS major >=14, and sets public WKPreferences.inactiveSchedulingPolicy. Apple's API defaults to suspension for inactive/detached views, with none/throttle alternatives; current minimum OS is compatible. [Apple API](https://developer.apple.com/documentation/webkit/wkpreferences/inactiveschedulingpolicy-swift.property), [WebKit public header and availability](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKPreferences.h).
- **Windows unsupported setter does not mean invisible WebView2 necessarily suspends.** Microsoft explicitly distinguishes invisible WebViews continuing script/network from application-requested TrySuspend, which pauses scripts. Visibility does throttle some activity; retain processing without TrySuspend and ensure checkpoint timers tolerate delay. This is a reason to probe actual execution rather than assume either permanent suspension or unthrottled progress. [Microsoft inactive-memory design](https://github.com/MicrosoftEdge/WebView2Feedback/blob/main/specs/MemoryUsageTargetLevel.md), [TrySuspend API](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2_3), [visibility behavior](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2controller.isvisible).
- Current pinned wry WebView2 implementation contains no TrySuspend call. `tauri-runtime-wry-2.12.1/src/lib.rs:3380` hides the native window; webview-specific Show/Hide is a separate path around `:3701`. Preserve that distinction in the spike. Do not manufacture a visible off-screen window or fake audio to defeat policy.
- Microsoft's browser flags page explicitly advises against production flags; **do not ship `--disable-background-timer-throttling`** as the reliability mechanism. The experimental timer wake-interval API is not a stable required dependency. [Official flag policy](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/webview-features-flags).
- App Nap, system sleep and forced termination remain separate from WK inactive scheduling. If actual host evidence identifies App Nap interference, investigate a scoped active-work ProcessInfo activity token with allowing-idle-system-sleep and release it on no work; do not globally disable sleep or App Nap by default. [Apple ProcessInfo activity](https://developer.apple.com/documentation/foundation/processinfo/beginactivity(options:reason:)). No such token exists in current source and no necessity has been measured.

### Single instance, activation and discoverable background

1. Preserve `create:false` and one literal main builder. Acquire a read/write, non-truncating `File::try_lock` in the fixed app/profile-private directory **before** building the main WebView or opening product storage. Keep the descriptor for the entire application lifetime, including hidden and draining states. Never unlink/recreate a held lock path. Rust's current 1.99 supports this stable-since-1.89 API on Unix and Windows without a new lock crate. Existing SQLite writer lock remains an additional storage boundary. [Rust File::try_lock](https://doc.rust-lang.org/std/fs/struct.File.html#method.try_lock).
2. Identity is derived from trusted startup bundle/config plus normal-vs-isolated profile/root, never argv/query string. Same product/profile must share one lock across versions; acceptance's separate bundle/root remains isolated. No semver feature allowing two incompatible product versions to run together.
3. The official **tauri-plugin-single-instance =2.5.1** is a known compatible **compared alternative, not a selected dependency**: published 2026-09-29, MSRV1.90, Tauri dependency `2.12`, no JS API/capability, Windows uses windows-sys0.61. If reconsidered, it must register before other ordinary plugins, have an exact reviewed pin and disable semver/deep-link. [Official plugin guide](https://v2.tauri.app/plugin/single-instance/), [published metadata](https://crates.io/crates/tauri-plugin-single-instance/2.5.1).
4. **Plugin caveat requiring concrete handling:** inspected published 2.5.1 macOS source uses a /tmp socket keyed by normalized identifier, removes the socket after NotFound/ConnectionRefused, binds in a spawned task, and logs then launches normally on notification/listen failures (`src/platform_impl/macos.rs:20-46`, `:95-129`). It is not a strict singleton proof. A product lock gate must fail closed even when activation fails. Do not enter a second product setup just because plugin setup returns Ok. Startup races must prove the losing process cannot unlink/replace the primary activation endpoint. If selecting the plugin, resolve that race in the bounded spike or a narrow provenance-preserved adapter before source delivery; do not declare the stock plugin alone sufficient. [Published crate source](https://docs.rs/crate/tauri-plugin-single-instance/2.5.1/source/src/platform_impl/macos.rs).
5. **Selected activation contract:** hold the lock first, bind native `127.0.0.1:0`, atomically publish private port+nonce metadata under that app/profile's native directory, and accept only a closed `{version:1,activate:true,nonce}` DTO with a <=256-byte frame, at most a small fixed number of concurrent readers and a short read deadline. Generate a fresh native random nonce for each acquired owner; metadata is private to the user (Unix directory0700/file0600; Windows app-private path/ACL). Never overwrite/truncate/unlink the held lock file or place tokens in argv/diagnostics. A losing launcher reads only that fixed metadata path and performs finite original-endpoint readiness retry (suggest <=2s) while the primary finishes main creation; it never builds a WebView/store. Primary activation before main-ready becomes a single coalesced show intent, applied after the one builder finishes. During Quit it returns closing; it cannot create another owner. A missing/stale port, bad nonce or failed activation produces bounded failure, not a second window. Only successful lock acquisition authorizes startup; stale metadata cannot. The only successful action is Show/Unminimize/Focus: **zero model calls, tool calls, route changes, project selection or run resume**. There is no public HTTP service, command proxy, JS eval or arbitrary args/URLs/paths. Existing Tokio net+uuid suffice. This avoids unstable private plugin sockets and extra dependencies, at the cost of a small local listener and installed firewall acceptance.
6. Build Windows tray and macOS Dock/menu presence before enabling hide-on-close. Native tray requires Tauri's `tray-icon` Cargo feature; tray-icon0.25.1 is already present in Cargo.lock, but feature activation still changes the effective native build. Rust owns menu/tray; no broad renderer tray/window-create capabilities. Include Show/Open and explicit Quit. macOS `RunEvent::Reopen` (tauri2.12.2 app.rs275) shows the same main; Windows tray click does likewise. [Official tray guide](https://v2.tauri.app/learn/system-tray/).
7. Lock failure must not fall through into a product UI. Known competing owner follows activation-only path; actual filesystem/lock errors report a bounded startup failure. If required tray/menu presence cannot be established, do not silently hide an unreachable app; fail lifecycle setup visibly before admitting background work. Existing main show/unminimize/focus errors must remain observable safe diagnostics, not create a replacement main.

### Explicit Quit / drain and current authority

- Change builder.run into build+run callback. `RunEvent::ExitRequested` (tauri2.12.2 app.rs220) can be prevented while a native Quit state machine transitions from running to quiescing. `AppHandle::exit` itself triggers ExitRequested/Exit (app.rs574); use one idempotent Quit coordinator and allow the final exit only after the coordinator's terminal phase, avoiding recursive prevention. A native atomic/mutex transition owns exactly one shutdown generation, deadline and actual drain task; repeated menu/shortcut/tray Quit only observes that same task. Lifecycle acknowledgements bind its original epoch and actual bundled main sender. They cannot restart a deadline, reopen admission or finish a replacement generation.
- CloseRequested hides only while not quitting; never invokes `close_product`, a reload, JS service disposal or a fresh session. Window destruction/reload retains current authority invalidation behavior. Reopen means attach to the surviving owner, not recover-and-resubmit.
- Quit synchronously closes new service/run/native effect admission first. Signal all actually owned per-thread controllers, retain their original completion promises and await finite stop/drain. UI hidden/route disposal cannot be a stop command. MCP connections are shared application services: stopping thread A must not dispose B's connection; app Quit eventually disposes the host after thread settlement/publication.
- Keep storage/session open while accepted original output, unknown outcomes and confirmed late replies settle. Then dispose MCP using its existing original drain ownership, stop media/process groups/Job Objects, close save/import/preview/read owners, and finally close the product worker. `invalidate()` and `abort()` are not completed drain receipts.
- Define a finite shutdown deadline (suggest 5 s initial grace, same retained drain on repeated Quit). Deadline expiry ends the application without inventing remote cancellation or completed local drain. Persist only established certainty; a lost remote reply remains unknown. Native cleanup must not require an indefinitely responsive renderer: an absent/unresponsive frontend takes bounded native cancellation then cold-start reconciliation.
- Cold startup under the new held singleton/thread ownership interrupts stale runs and reconciles existing jobs/status/receipts; it makes zero fresh model/tool/effect dispatches. MCP saved IDs/snapshots do not reconstruct private host bearer authority. Sleep/network interruptions similarly preserve unknown outcomes without automatic replay.

## Caveats / Not Found

- This is planning research only. No product code, dependencies, task activation or Git state were changed; no build/package/install or paid request was run.
- No Windows host was exercised, and no >six-minute actual hidden WKWebView/WebView2 test was performed in this research. Current stock closing still destroys main. Background delivery is therefore not established.
- Actual linked/installer size of the new lifecycle/tray/plugin closure is unmeasured; 47,099 bytes is the published plugin's compressed **source crate** size, not installed size. Avoid presenting the machine Node executable size as a target package estimate.
- Official main branches can advance; pinned cached sources and published 2.5.1 crate were used to check compatibility. The plugin's current v2 branch advertises 2.5.4 and must not replace an exact reviewed pin without review.
- The activation transport selection is now closed: std file lock plus existing Tokio bounded native endpoint. The implementation spike still needs to prove readiness contention, stale metadata, lock release/crash and single Show/Focus behavior. The invariant is fixed: no second product window, store or run owner on activation failure or launch contention.

### Final design / Stage 3 consistency review

Reviewed the authored `design.md` native/Quit sections and `implement.md` Stage 3 on 2026-10-16. The selected retained-main service, std/Tokio singleton gate, supported macOS scheduling, no Windows production flags, original-resource drainage and deferred installed evidence agree with this research. No material architecture contradiction was found. Two necessary implementation boundaries should be made explicit before Stage 3:

- A tray/Dock Quit with a retained dirty editor must show/focus the one main window before presenting its existing unsaved-change protection. A missing/unresponsive renderer cannot leave native Quit waiting indefinitely before the grace period; it takes the same bounded fallback. Ordinary close-to-hide needs no new leave prompt and does not discard that draft. Treat cancelling a responsive existing dirty-editor guard separately from an accepted Quit intent.
- The 5-second cooperative grace must be followed by a single **explicit globally bounded** native cleanup budget (suggest <=2 additional seconds), rather than sequential full per-resource Stop timeouts. Repeated Quit joins the same deadline/task. Exceeding either budget does not manufacture a drained receipt or remote cancellation; it exits with whatever certainty was actually retained and relies on no-replay cold reconciliation.

Activation implementation also needs numeric admission/read/connect limits and a closed bounded acknowledgement (accepted, closing or not_ready). Coalesce pre-main-ready activation; no receipt can mean a new model/tool dispatch, route change or permission grant. These refine the already selected protocol rather than require another transport/dependency decision. This review ran no implementation, test, build, dependency or Git action.
