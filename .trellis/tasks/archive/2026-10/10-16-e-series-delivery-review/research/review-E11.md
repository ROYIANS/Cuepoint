## 1. Verdict

Source-level quality of the Studio service is good and unusually well tested. The Rust lifecycle state machine is carefully built. The weak points are (a) platform evidence: only a macOS debug probe, no Windows/WebView2, no real explicit Quit through the native stack; (b) the architectural bet that all execution lives in a WebView JS context (dsh uses a separate Host process); (c) several robustness edges in startup recovery, Quit guard timeout and in-memory-only drafts. No P0. Two P1s are mostly "claimed more than verified".

## 3. Findings

### P1

**P1-1. Execution authority lives in a WebView JS context; OS/WebView termination while hidden is unhandled and unverified.** [code]
The service, drafts, MCP connections and thread work are module state in the one WebView (`agentExecution.ts:5`, `chatDraftStore.ts:155`, `threadWork.ts:16`). On macOS WKWebView web-content-process termination (memory pressure while hidden) or Windows WebView2 `ProcessFailed`/crash kills every in-flight run at once. No handler exists (`rg ProcessFailed|content process` in `R/` = none; only `PageLoadEvent::Started` detaches the lifecycle, `desktop.rs` diff). After reload the runs are reconciled to "interrupted" (safe), and drafts/attempts are lost (see P2-3), but there is no user-visible "background work was interrupted" signal and no detection that a hidden window's WebView died. The 370 s probe does not cover this. dsh runs the agent in a separate Host process (`apps/desktop/src/host-process.ts`, `apps/desktop-host/src/index.ts`) so a renderer crash does not stop work. Severity P1 because this is the stated core outcome ("retain background execution") and the only evidence is one macOS debug run, which the task itself records with an unexplained failed earlier probe (results.md Stage 3: attempt `if5hwj` exited 0 after ~205 s, cause unproven).

**P1-2. AC8 and Windows parts of outcomes 4/5 are ticked/claimed on fake-port tests and macOS-only evidence.** [claim-only / test]
See table rows 4-6. Specifically no real-window test of: hide -> Quit from tray with active runs -> `RunEvent::ExitRequested` handling (`desktop.rs` run closure) -> `request_quit` -> drained ack -> `app.exit(0)`. The one place the real path matters most (`native.rs:171-264`) has a 1 s guard timeout, a 5 s drain deadline and a 2 s native deadline that are only exercised in production. Recommend re-labelling AC8 "Partly" until installed acceptance (the PRD already defers AC3).

### P2

**P2-1. Quit bypasses the manual-draft guard if the renderer does not answer within 1 s.** [code] `native.rs:180-199`: `initial` timeout -> `initial.is_ok()` false -> skips the human wait -> `quiesce`. Intent: "native owns absent-renderer fallback", but a hidden/throttled or busy renderer (two streaming runs, large transcript) can legitimately take >1 s, silently discarding dirty manual business-editor drafts that the guard exists to protect (`manualQuitGuards.ts:16`, `applicationQuit.ts:26-37`). Prefer: timeout -> treat as `decision_required` and show the window, or extend the budget when the window is visible. Test gap: nothing covers slow-but-present renderer.

**P2-2. No confirmation or notice when Quit/close affects running work or first hides to background.** [code] Quit never asks even when runs are active (guard only counts manual drafts, `manualQuitGuards.ts:16`); closing the window hides with no first-time notice (`desktop.rs:2014-2024`). dsh counts active agents/jobs/queued messages and confirms (`apps/desktop-host/src/quit-inspection.ts:1-40`, `apps/desktop/src/quit-confirmation.ts`) and shows a one-time Windows tray notice (`apps/desktop/src/background-notice.ts`). Product accepted "explicit Quit ends it", but a paid generation being aborted by Cmd+Q without warning is a divergence the PRD did not decide; at least the discoverability of "app still running" on Windows (users may think close = exit) is unaddressed.

**P2-3. Drafts, failed/uncertain submission attempts are memory-only.** [code] `chatDraftStore.ts:10-14` (plain `drafts` object, no persistence); service `attempts` array `agentExecutionService.ts:50`. Within the retained process this is the PRD scope ("within app/document lifetime"), but combined with P1-1 any WebView reload/crash/forced exit loses unsent text and the "uncertain, please verify" affordance (admission itself is durable, so the check is recoverable only if the user knows to look). Also `drafts` map never evicts entries for deleted threads (`chatDraftStore.ts:15-27`, no delete hook) and keeps `File` objects for failed imports; slow leak in a long-resident app (P3 in isolation, P2 given always-resident lifetime).

**P2-4. Startup reconciliation is all-or-nothing and permanently memoized on failure.** [code][test] `agentExecutionService.ts:135-142` memoizes `initialized` even when it rejects; `bootstrap.tsx:62-66` awaits it so one bad thread row/lock error makes the whole app render "工作区无法打开" (`:75-85`), and `runOwnership.ts:83-96` has no per-thread try/catch, so one failing thread stops reconciliation of all others. Test `agentExecutionService.test.ts:329-345` pins the "rejection stays memoized" behaviour as intended. Safer: isolate per thread, report per-thread "needs attention", never block boot.

**P2-5. `Closing` contender silently fails.** [code] `native.rs:67-75`: a second launch during Quit gets `Ack::Closing` -> `exit(1)`: no app, no message. A user relaunching right after Quit within the drain window sees nothing happen. Acceptable but should retry/wait or at least be documented in installed acceptance.

**P2-6. No handling of OS session end / Windows shutdown with hide-on-close.** [code] `CloseRequested` is always `prevent_close`d (`desktop.rs:2016-2018`, no `ExitRequested`-independent bypass, no session-end flag; `rg session|ENDSESSION` in `R/` = none). On Windows logoff/shutdown the OS sends close; a hidden-but-vetoing window can stall shutdown or get force-killed mid-write. dsh explicitly tracks `sessionEnding` and lets close through (`apps/desktop/src/main.ts:1060-1080`) and handles macOS fullscreen before `hide()` (`main.ts:1064-1070`); ours has no fullscreen handling (`rg fullscreen R/` = none; hiding a fullscreen macOS window leaves a black space). Unverified [claim-only] on real OS; flag for installed acceptance.

**P2-7. Custom TCP loopback activation instead of platform single-instance primitive.** [code] `singleton.rs:226-300` opens a loopback listener (nonce, 256 B frames, 8 slots, 1 s IO) plus private metadata file; dsh uses `requestSingleInstanceLock` + `second-instance` (`apps/desktop/src/single-instance.ts:1-26`). The design is careful (lock first, nonce per owner, bounded) and documented as chosen over `tauri-plugin-single-instance` for unstable plugin sockets, but it adds a local listener (firewall prompts on Windows are listed as unverified) and a larger audit surface. Not wrong; flagged as weaker-by-complexity.

**P2-8. Service robustness edges.** [code]
- `claim()` reserves thread work (`agentExecutionService.ts:150-151`) before `feedbackOwner.begin(...)` at `:156`; if `begin` throws the reservation is never `follow`ed, leaving the thread permanently "busy" (`threadWork.ts:34`). Move `begin` before reserve or wrap with release.
- In `claim`'s catch `attemptFor(...)` (`:173`) can throw "发送记录不存在" if the attempt was removed; then `rejectDone` is skipped, `done` never settles and `reservation.follow(done)` never cleans up (thread stuck). `dismissAttempt` guards on `owner.invocation` (`:373`) so currently unreachable, but the invariant is implicit.
- `shutdown()` snapshot only waits on invocations present at call time plus `shutdownAgentThreadWork`; there is no own deadline (native owns it, 5 s `native.rs:215`). Tool effects that ignore abort will hold the "drained" status until native gives up; correct and honest ("original outcomes remain unconfirmed", `native.rs:225-229`).

## 4. Specific review points

- **Application-owned service lifecycle:** one module-level instance (`agentExecution.ts:5`), `claim` is synchronous up to reservation, opaque branded token (`:16-18`), Object.freeze snapshots, listeners isolated by try/catch. Sound. Reservation published before feedback (`:150-160`) with the P2-8 caveat.
- **Races:** duplicate send on same thread blocked by `owner.invocation` + `reserveAgentThreadWork` (two layers); Stop vs completion: `requestStop` checks token identity (`:349`) so stale tokens cannot abort a newer invocation; B cannot release A (per-thread maps). Quit vs new claim: `admissionOpen` checked first (`:145`) and again in `reserve` (`threadWork.ts:33`) and `productEffectAdmission`. Deletion vs run: stop + `await work.done` before delete (`AgentChatPage.tsx:295-300`). Unread ack vs newer revision: acknowledged revision comes from the presented revision, rejects `> publicRevision` (`commands/threadActivity.ts:77`) and cannot clear newer ones (`:76`).
- **Reattach to authoritative state:** views read `agentExecution.snapshot` + DB queries, no ID-based dispatch; saved IDs cannot authorize (token is a private symbol-branded object). Good. After process restart nothing can reattach by design.
- **Draft protection:** revision-checked `restore`/`moveTo` (`chatDraftStore.ts:104-160`); sound for in-process lifetime, see P2-3 for persistence.
- **Rust/Tauri hiding:** `prevent_close + hide` is minimal and correct for single-window (`create:false` literal main builder, `desktop.rs` setup). Missing: fullscreen/session-end (P2-6), `ProcessFailed` (P1-1). `WindowEvent::Destroyed` -> detach + close_product is only reached via real exit.
- **Quit idempotence:** native `begin()` single-intent; ack validation ties intent id + attached session + storage generation (`mod.rs:188-238`, `desktop.rs product_lifecycle_request`); TS side joins `active.drain` (`applicationQuit.ts:39-47`). Good. `acknowledge` after `detach` rejected (test `mod.rs:354-377`).
- **No automatic effect replay:** `claim` only runs on explicit user action; `initialize` runs repair-only code (`runOwnership.ts:76-97`); `resolveChatRunAction` approve/resume require user actions and re-check outstanding approvals (`chatExecutionFlows.ts:133-134`); `retry` of submit first reads receipt and never dispatches on `accepted` (`agentExecutionService.ts:213-219`). Supported by test `agentExecutionService.test.ts:362`.

## 6. Integration seams (cross-delivery inputs)

- **E02 optimistic send <-> E11 service:** attempts moved into the service (`chatSubmissionAttempt.ts`, `agentExecutionService.ts:56-74,245-262`); `submit` accepts `afterOptimisticPaint` (`:243,250`). Optimistic bubble identity survives navigation; accepted attempts are retained until the reader dismisses them, and the owner-reported `发送记录不存在` crash was fixed by idempotent `dismissAttempt` [test `agentExecutionService.test.ts:132`]. Seam risks: attempts are memory-only (P2-3); `submit` rejects duplicates only by userMessageId in the same thread map (`:246`), new-topic scope attempts are found through `attemptsForScope` and rely on `publish` recomputing all scopes on every publish (`:108-116`) — O(threads x attempts) per publish while streaming (3 listeners) — fine now, scale caveat.
- **E03 execution feedback <-> E11:** feedback controller created per thread (`:89-94`), `lastFeedback` retained after release (`:161,363-366`) so a reattached view sees the final phase [test `:347`]. `feedback` updates publish only while `owner.invocation` is set (`:93`), so feedback emitted exactly after release is dropped by design. `controlOwner` zeroes `outputRevision` in the page snapshot (`useChatExecutionSession.ts:18`) to avoid per-token rerenders — consistent with chat-performance spec. No conflict found.
- **E07 jobs / audio-video batches <-> E11:** batches reserve the same per-thread slot (`audio batchRuntime.ts:66,83,155-157`; `video generationBatchRuntime.ts:52`), so a running batch blocks a new model claim (`threadWork.ts:34`) and shows as busy in the sidebar. Behavioural consequence: user cannot send in a thread while its batch runs (matches "exclusion within one conversation"). Audio code binds `follow` in two branches (`:155` vs `:157`); correct today because `agentThreadId` selects exactly one, but fragile.
- **E10 MCP session authority <-> E11:** MCP runtime/registration is a document-lifetime singleton (`mcp/runtime/owner.ts`), so it survives hide; `beginAgentRun` pins the snapshot (`agentRuns.ts:92,241`) and exact Stop/status reach the same connections. Quit disposes MCP only after agent/native stops settle and downgrades outcome when `draining` (`applicationQuit.ts:53-54`, `desktopApplication.ts:28-33`) [test e11McpQuit]. Seam risk: `store reopen` on webview reload `invalidate_mcp` (`desktop.rs product_store_request`) correctly drops authority; no shared guarantee that a reload while hidden surfaces to user (P1-1). OAuth callback while hidden: `oauth.rs` was changed in 59701819 but window show on callback not verified [claim-only].
- **E06/E07 contracts:** report revisions feed unread (`publishAgentReportActivity`, `commands/threadActivity.ts:51-63`) tied to `agentJobs`; deletion removes the activity row (`lifecycle.ts` diff) — consistent.

## 7. Summary of top findings

1. **P1-1** Core outcome rests on a WebView surviving hidden; no crash/termination handling and only a single macOS debug probe (plus an unexplained earlier failed probe); dsh isolates in a Host process.
2. **P1-2** AC8 / Windows evidence is fake-port or macOS-only; real hide -> Quit -> exit with active runs never exercised.
3. **P2-1** 1 s guard timeout lets Quit skip the manual-draft decision for a slow renderer.
4. **P2-2/P2-6** No running-work Quit confirmation, no background notice, no session-end/fullscreen handling (dsh has all three).
5. **P2-3/P2-4** Drafts/attempts memory-only and unevicted; startup reconciliation is all-or-nothing and can block boot.
6. Service core (reservation, tokens, Stop isolation, shutdown, no replay) is solid; targeted 40 tests pass. No P0.
