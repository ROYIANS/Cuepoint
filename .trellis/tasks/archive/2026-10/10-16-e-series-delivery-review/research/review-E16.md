## Findings

### P2-1 Handoff has a single point of failure and no watchdog: it depends on Radix `onCloseAutoFocus` firing
`activateTarget` sets `handoffRef.current` (phase "releasing") and `setHandoff(true)` (`AgentGenerationBatches.tsx:371-378`); the only call that advances to `openDetail` is `queueMicrotask(openAfterModalRelease)` inside the dialog's `onCloseAutoFocus` (`:431-436`). If that event does not fire (e.g. Content unmounted by a parent re-render during the same tick, reduced-motion/Presence differences, a future Radix change), the state stays `releasing`: the modal is hidden (`open && !handoff`, `:418`), further target clicks early-return after `preventDefault` (`:371` returns *after* `event.preventDefault()` at `:370`, so the link silently does nothing), and `revealReview` only sets `returnRequested` (`:222-224`) – the user cannot reopen the review except by leaving the page, while the (still-dirty) `local` draft blocks route changes via `useBlocker` (`:~290`). Tests exercise the happy event in jsdom (`e16BatchDetailHandoff.test.ts:209-312`) but not "event never fires". Suggest a bounded timeout fallback that calls `openAfterModalRelease` (or restores the modal).

### P2-2 Residual entity families have no owner after E12–E15 cancellation
The roadmap says "Other families retain explicit navigation/follow-up scope" (`.../10-15-agent-experience-desktop-evolution/roadmap.md:14`), the spec says "later … work must establish exact identity" (`agent-business-details.md:84`), but no task exists for material (`/assets` collection link has no entity identity, `materialTools.ts:188`), IP, memory (`?memory={id}` already has exact identity), project/episode, audio/music. R1 asks to define "supported coverage *and rollout*"; the rollout beyond the slice is a prose promise only [claim-only]. Not a code defect, but the PRD AC "Each supported entity opens its correctly owned detail" is satisfied only by narrowing "supported".

### P2-3 Handoff finishing on `replaced` closes the review silently while a dirty draft remains
`endOrigin → finishHandoff(token, restore=false)` (`:359-363`, `:213-219`) sets `open=false` but keeps `local` and the route blocker. After a second detail (or a competing context panel) replaces the one opened from the review, the review modal does not reopen; the draft is retained but invisible except via the batch card. Deliberate ("do not open its modal over the new detail", comment `:217`), test `e16BatchDetailHandoff.test.ts:229`, but no UI affordance tells the user about the retained unsaved edits besides the route blocker.

### P3-1 Batch target activation is inert outside the Agent provider: `activateTarget` returns early when `useBusinessDetails()` is null (`:371` via `openDetail`), falling back to a normal in-modal navigation link. Since the provider lives in `AgentChatPage` (`AgentChatPage.tsx:60-62`, see E01 P2-2) any future host of `BatchSurface` outside that page silently regresses to route navigation with a modal still open.
### P3-2 `readBusinessDetailTarget` for assets rejects any `?`/`#`/`\` (`businessDetailTarget.ts:20`) – good for allowlisting, but producers that later append `?slot=` etc. silently lose activation (graceful fallback). No test pins the current producers (`businessStore.ts:271-276`, `generationTargetDestination.ts:18-24`) against the parser for all four kinds × two owners except via `businessDetailTarget.test.ts`.
### P3-3 Pre-existing `useManualDraftDeparture` quirk exposed by E16's two panels: when an earlier local request completes because the draft became clean, the *new* request is cancelled even though state is now clean (`useManualDraftGuard.tsx:85-95`). Unreachable via the panels' `switching` latch, but fragile.
### P3-4 `AssetDetailPanel`/`ShotDetailPanel` duplicate ~60 lines of request/close/outcome state machine (`AssetDetailPanel.tsx:17-64` vs `ShotDetailPanel.tsx:39-111`); a third family will copy it again. Consider extracting a `useDetailPanelSession` hook.
### P3-5 E16 touched four asset detail pages (≈ -600/+600 lines moved to `assetDetailFields.tsx`, 474 lines). Route pages and panes share one body (good), but the changed route pages are only covered through `e16AssetDetailPanel` + existing page tests; a route-level regression test for all four kinds was not found [claim-only].
