## Read and ownership semantics

`src/db/media.ts:6` collects current durable references with no transaction of its own. Without an argument every owner is read, including archived projects and studio assets; with an argument every row is filtered by its `projectId` (projects by `id`). `projectId` on assets/media is an owner ID: `studio` is valid without a projects row (`src/domain/types.ts:8–13`, `src/db/productionShared.ts:27–34`). Global reads do not validate each referencing row’s owner against the candidate. Backup calls `collectMediaIds(projectId)` inside its readonly snapshot (`src/lib/projectPackage.ts:81–125`); preserve this projection and keep proposal/image generation history separate.

`deleteMediaIfOrphan` (`src/db/media.ts:66–85`) always enters an rw `PRODUCTION_TABLES` transaction, skips undefined/missing candidates, reads the candidate record, then collects global current references and four history collections scoped to **that record.projectId**. It deletes only if all retention conditions are false. All four history reads happen even when current content already retains the candidate. Ownerless global history union would broaden today’s foreign-owner-history behavior; caller-project-only history would lose valid mixed-owner retention.

Do not silently add/remove retention sources under the batching change.

This is the one current production function-value injection, in addition to 17 direct named invocation sites. It must not be lost when preserving the scalar orphan API.

`deleteEpisodeShots` (`src/db/shots.ts:418–441`) is an additional **nested entry**: validates project/episode/unique requested rows, bulkGets deduplicated media for undo, then awaits deleteShots under the same production lock; snapshot success comes only after cleanup. reindexShots reads/writes shots (`:38–44`), listEpisodes reads episodes (`src/db/episodes.ts:28–31`). Do not move deletion/snapshot outside the root transaction. Missing/stale/CAS/kind/parent guards and timestamp/order/relationship effects in caller rows stay intact.

`deleteProject` (`src/db/cascadeCommands.ts:31–85`) is an intentionally separate direct cascade, **not** an orphan-helper caller: one rw transaction deletes all AUDIO_TABLES rows for owner, material uses/link, project refs/chunks/memories/versions, batch/items/jobs/proposals/assets/episodes/shots, owner media, then project; library project-scope snapshots are archived with events, shared snapshots survive. Do not replace this with child commands or global GC. deleteChatThread has one broader root lock and cleans orphan candidates only after its own histories are removed; proposals/audio and other thread histories may still retain them.

**releaseMaterialUse batching constraint:** validate use/target and other-use conflicts inside the original `PRODUCTION_TABLES + materialEvents` rw transaction; remove use; unmark `libraryRetained` for **all use.mediaIds copies being released before taking the batch retention snapshot**; only then collect fresh current/history retention and delete eligible candidates. Reject if any candidate still exists; add the release event last. Keep the post-delete existence check and complete rollback, including earlier deleted copies and flags when a later copy remains or event fails. Current code unmarks/deletes/checks one ID at a time (`src/db/assetReuse.ts:25–39`); taking one snapshot before the remaining flags are cleared produces false retained copies. Normal adoption owns copied media, but release itself adds no per-media owner check—do not describe one as existing.

Agent material release adds another outer boundary: `src/lib/agent/materialTools.ts:499` calls releaseMaterialUse through `libraryWriteTool`; `src/lib/agent/libraryToolHelpers.ts:98–105` awaits executeAtomicTool, rechecks preview revision, then options.execute. Thus material release is nested under generic db.tables when invoked as an Agent tool; the UI call enters the release command directly. Both require event/deletion failures to propagate.

Installed Dexie is 4.4.6 (local input, not a version recommendation). Its actual implementation (`node_modules/dexie/dist/dexie.mjs:6154–6215`, `:4697–4698`, `:3173–3184`) rejects rw-under-readonly or child stores absent from parent, shares parent.idbtrans for compatible nested transactions, and propagates failure to parent/abort. Existing rw mode has no `!` or `?`; do not escape into an independently committed transaction or swallow cleanup failures. `executeAtomicTool` (`src/db/agentTools.ts:343–365`) retains db.tables plus run/thread/permission checks, callback, receipt/result and abort as one atomic boundary. No provider/fetch/hash/ZIP work belongs inside these write transactions. One retention snapshot is per explicit cleanup operation after its relevant writes, not an ambient transaction-wide cache reused after subsequent writes.
