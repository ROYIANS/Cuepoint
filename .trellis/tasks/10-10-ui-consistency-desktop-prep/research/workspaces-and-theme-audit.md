### 4. Reuse opportunities without business refactors

- **Semantic global tokens** for canvas, panel, elevated overlay, subtle separator, muted/secondary text, selected/hover, focus, status, spacing, content gutter and named title roles. Global tokens already exist (`styles.css:6–76`); evolve them instead of adding independent feature palettes.
- **PageHeader / PageContent presentation primitives** with title, supporting copy, optional context, actions and width/density variants. Strong initial consumers: series episodes, story, produce, world, shared asset details, memory and task board. Avoid database/routing side effects in primitives.
- **WorkspaceToolbar** presentation geometry: project header, secondary chapter/shot toolbar and compact controls can share spacing/type/status roles while retaining action ownership. Do not bury context and approval state in cosmetic overflow menus.
- **Empty / loading / error / unavailable state presentation**, with distinct semantic types and page/panel/inline variants; existing `EmptyState` in `audioMusic/shared.tsx:42–43` is sound-specific rather than a global solution.
- **Overlay role classes / composition** using current Dialog/Sheet, not a replacement dialog engine. Keep form/scroll body/footer separated where needed; avoid global feature selectors rewriting all controls.
- **Agent theme adapter** plus shared task/document heading roles. Rich ChatItem, model selector and composer remain LobeHub/antd-scoped. `getPopupContainer` must still target the local Agent or current dialog (`ChatWorkspace.tsx:41–42`, `GenerationReview.tsx:41`).
- **Explicit density exceptions**: shot rows/canvas, manuscript paragraphs, time labels/track colors, chat content width, print grid. Tokens can be shared without making these identical to collection cards.

### 5. Desktop resize / keyboard / scroll preparation

This is preparation for the existing web UI. No Electron/Tauri/native framework, OS titlebar, traffic lights, window drag region, native menu, updater, platform bridge or minimum application size is selected.

1. Audit at wide desktop, ordinary desktop, narrow desktop, short window and phone widths. Include widths just above/below actual thresholds (640/700/760/768/800/1000/1100/1200/1280) for impacted families; use a focused matrix rather than exhaustively multiplying every page by every width.
2. Determine smallest usable width/height from real contents: project header wrapping and long names; shot toolbar/table; audio chapter/actions+inspector/timeline; music creation+worklist+player; memory list/detail; task board+inspector. Then agree collapsible/drawer/mode transitions before asserting a supported minimum size.
3. Keep a single bounded root height and intended inner scroll owners. Preserve min-h-0/min-w-0 throughout flex/grid ancestors. Native checks should record client/scroll widths and a full screenshot, not infer usability from a width token alone.
4. Test Tab/Shift+Tab, Escape, Enter/Space, arrows, visible focus, focus return, scroll-to-focus, open menus near edges and dialogs in short windows. Scrollbars differ across platforms; functional width must survive permanent scrollbars rather than rely on macOS overlay behavior.
5. Preserve reading/stream intent: existing Agent header/composer are overlays, composer safe-height is measured (`ChatWorkspace.tsx:93–103`), transcript is independent (`agentChat.css:584–596`), dock pointer-events routing remains precise (`:605–642`). Do not replace this with whole-page scrolling or smooth token-by-token scrolling.
6. Hover-only small editor controls need touch and keyboard verification. Keep disclosure/list controls accessible and don't hide destructive controls so that only pointer hover can reach them.
7. Resize open overlays and active editors, not only resting pages. Draft, focus, selection and current playback must survive the transition between permanent pane and Sheet/mode layout.
8. Test local/offline font fallback and reduced-motion preferences; preserve original accessible semantic status labels. Status color on its own cannot carry approval, uncertain, error or completion state.

### 7. Proposed staged audit and implementation order

1. **Coverage first**: merge this family inventory with Studio/IP/Material Library/settings audit; enumerate route screen, redirect, nested layout, each shared detail owner and visible state/overlay. Mark source/native review separately. Start actual comparison with the user's Projects versus Material Library example.
2. **Baseline decision**: present existing visual directions with native screenshots. Agree functional H1/description/action contract, serif/sans roles, page and editor density, surface hierarchy, widths/gutters, control roles and supported appearance. Add explicit print/welcome/canvas exceptions. This is the planning review gate, not automatic aesthetic selection.
3. **Foundation and representative pair**: shared tokens/presentation wrappers + Projects/Material Library; verify wide/narrow and overlay focus before broad rollout. Add scoped Agent adapter without global reset/theme leakage.
4. **Document/management screens**: episode list/story/produce/world/shared details/memory/task board. Share page header/gutters/state presentation; retain detail/sidebar scroll semantics and existing ownership/draft barriers.
5. **Dense workspaces**: shots, audio and music. Align outer chrome and compact toolbar roles, then panel/drawer/mobile tiers. Preserve table row anchors, timeline geometry, manuscript behavior, real media duration and paid confirmation. Work in independently owned feature chunks with integrated review after shared foundations.
6. **Agent and overlays**: welcome/conversation/task inspector/documents/model/context/generation/run details, dialogs/Sheets/popovers. Validate mounted runtime, portal theme scope, long titles, composer masks/safe areas, dirty/pending close and approval visibility.
7. **Native acceptance and contract update**: before/after pairs, narrow and short windows, populated/empty/loading/error/details, keyboard focus/return, representative resize while open, print output. Required type/build/quality plus relevant existing behavior tests after implementation; update component/style spec to match final approved implementation. No browser screenshots or passes are claimed by this research.
